# KII Significance Service

Сервис помогает оценивать категорию значимости объекта КИИ по методике категорирования и показывает, как на результат влияют показатели `8.3.1-8.3.14`.

Проект состоит из двух основных сервисов:

- `inference-api` на `FastAPI` рассчитывает итоговую категорию, объяснение и вспомогательные вероятности модели.
- `dashboard` на `Streamlit` предоставляет интерфейс для ввода данных, просмотра результата и ведения локального реестра объектов.

Дополнительно есть каталог `model-training` со скриптами генерации датасета, дообучения и проверки модели.

## Что делает система

Текущая версия использует `двухконтурный` подход:

1. `Правило методики` определяет итоговую категорию.
   Итоговая категория берется как `наивысшая` из применимых показателей `8.3.1-8.3.14`.

2. `ИИ-модель` не подменяет правило.
   Она выступает как `supporting classifier`: дает дополнительный ML-сигнал, confidence и помогает обнаруживать нетривиальные сочетания признаков.

Это сознательное решение. Для задач КИИ лучше, чтобы юридически значимый результат считался по прозрачному правилу, а ИИ помогал интерпретировать и проверять входные данные.

## Что ИИ делает в системе

ИИ здесь помогает, но не принимает окончательное решение вместо методики.

ИИ:

- использует вектор признаков, совместимый с показателями методики;
- оценивает вероятность классов `0..3`;
- участвует в расчете confidence;
- помогает выделить ключевые факторы;
- может использоваться для обучения на синтетических и экспертно размеченных данных;
- полезен как второй сигнал рядом с rule-based логикой.

ИИ сейчас `не`:

- заменяет правило присвоения категории;
- не освобождает от экспертной оценки исходных последствий;
- не формирует автоматически полный комплект юридически значимых документов;
- не является самостоятельным основанием для официального категорирования.

Практически это означает следующее:

- `финальная категория` считается по методике;
- `ИИ` помогает как экспертный ассистент и дополнительный классификатор.

## Что пока вводит пользователь вручную

Сейчас пользователь задает:

- сферы деятельности объекта;
- тип объекта;
- контекстные признаки;
- применимость показателей `8.3.1-8.3.14`;
- уже рассчитанный уровень каждого показателя: `0 / 1 / 2 / 3`.

То есть текущий интерфейс ближе к режиму:

- эксперт рассчитывает уровни показателей;
- сервис автоматически агрегирует их в итоговую категорию;
- ИИ помогает объяснить и дополнительно оценить результат.

Следующий логичный этап развития:

- перейти от ручного ввода уровней `8.3.*` к вводу `сырых исходных метрик`;
- автоматически рассчитывать уровни каждого показателя по таблицам и порогам;
- оставить ИИ как помощника для извлечения, проверки и объяснения.

## Нормативная основа

Сервис ориентирован на следующую нормативную базу:

- Федеральный закон от `26.07.2017 № 187-ФЗ` `О безопасности критической информационной инфраструктуры Российской Федерации`
- Постановление Правительства РФ от `08.02.2018 № 127`
- формы и сведения, связанные с категорированием и направлением результатов

Важно: сервис покрывает именно `логику категорирования`, а не весь полный контур compliance-процесса.

## Назначение ключевых файлов

- `kii_methodology.py` - общая методическая схема: 14 сфер, 14 показателей, нормализация входов, rule-based категорирование, feature vector.
- `inference-api/app.py` - API, расчет результата, загрузка модели, fallback и выдача explanation.
- `dashboard/app.py` - веб-интерфейс для заполнения формы и просмотра результата.
- `model-training/generate_synthetic_data.py` - генерация синтетического датасета под новую схему.
- `model-training/finetune_kii.py` - дообучение модели на схеме методики.
- `model-training/validate_inference.py` - проверка, что API реально поднимается и использует модель.

## Локальная подготовка окружения

Команды ниже рассчитаны на `PowerShell` и запускаются из корня проекта.

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -r .\model-training\requirements.txt

```

`httpx` нужен для `fastapi.testclient`, который используется в `model-training/validate_inference.py`.

## Генерация датасета и обучение

### Генерация нового синтетического датасета

```powershell
cd .\model-training
python .\generate_synthetic_data.py
cd ..
```

По умолчанию датасет сохраняется в:

- `model-training/synthetic_kii_data.csv`

### Дообучение модели

```powershell
cd .\model-training
python .\finetune_kii.py
cd ..
```

После обучения ожидаются:

- `inference-api/models/model.keras`
- `inference-api/models/model.h5`

## Проверка модели до запуска сервиса

```powershell
python .\model-training\validate_inference.py
```

Успешная проверка обычно означает:

- `model_loaded: true`
- `model_usable: true`
- `model_role: supporting_classifier`

Если в контейнере `model.keras` не читается из-за несовместимости сериализации, API может автоматически переключиться на:

- `model.h5`
- или `weights-only fallback`

Это нормальный рабочий сценарий для текущей сборки.

## Что делает Docker-конфигурация

`docker-compose.yml`:

- собирает `inference-api` из корня проекта с `inference-api/Dockerfile`
- собирает `dashboard` из корня проекта с `dashboard/Dockerfile`
- копирует общий `kii_methodology.py` в оба контейнера
- поднимает API на `8008`
- поднимает dashboard на `8501`
- включает fallback загрузки моделей

## Как работает загрузка модели

API пытается загрузить модель в таком порядке:

1. обычная загрузка `.keras` или `.h5`
2. ручная загрузка архива `.keras`
3. `weights-only fallback` из `.keras`
4. `weights-only fallback` из `.h5`

Если `model.keras` не читается из-за несовместимости `InputLayer`, это не считается фатальной ошибкой, пока сервис смог поднять рабочую модель через fallback.

## Проверка API после запуска

Быстрая проверка:

```powershell
curl http://localhost:8008/health
```

В рабочем режиме ожидаются:

- `status: ok`
- `model_loaded: true`
- `model_usable: true`

Поле `model_source` покажет, какая именно модель используется:

- например `model.keras`
- или `model.h5 (weights-only fallback)`

## Ограничения текущей версии

- используется синтетический датасет, а не промышленный корпус реальных кейсов;
- пользователь пока задает уровни показателей `8.3.*` вручную;
- автоматического расчета всех показателей из сырых первичных метрик пока нет;
- вместо БД используется локальный JSON;
- подготовка официальных форм и актов не автоматизирована полностью;
- сервис помогает категорировать, но не заменяет полноценную юридическую и методическую процедуру.
